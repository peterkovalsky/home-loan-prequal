# Phase 3: Deploy the API to AWS Lambda

Status: **done.** Live at `https://wmq0xra270.execute-api.ap-southeast-2.amazonaws.com/api`, deployed automatically from `main`. See "As built" at the end. Parent plan: [00-overview.md](00-overview.md).

## Goals

1. The Phase 2 API runs on **AWS Lambda behind HTTPS** (API Gateway HTTP API), with **no application code changes**: the same `AddAWSLambdaHosting` switch, packaged as a **container image**.
2. A **real SQL Server** (RDS SQL Server Express 2022, private), migrated automatically on every deploy.
3. **No manual deploys.** Every push to `main` that passes CI deploys, then proves itself with a smoke test and the Playwright suite against the live API.
4. Secrets never in code, environment variables or GitHub. IAM scoped to what each piece needs. Teardown is one click.

## Architecture

```
GitHub Actions (push to main, CI green)
  │ OIDC → IAM role "homeloan-github-deploy" (trusted only for this repo, branch main)
  │        └─ can only assume the CDK bootstrap roles
  ▼
cdk deploy ─► CloudFormation
               ├─ HomeLoanData stack
               │    VPC (2 AZs, isolated subnets only, no NAT, no internet gateway)
               │    RDS SQL Server Express (private SG; 1433 open only to the Lambda SG)
               │    Secrets: admin (generated by RDS) + homeloan_app (generated)

               └─ HomeLoanApi stack

                    Lambda "migrator"  ← CDK Trigger runs it on deploy; failure fails the deploy
                    Lambda "api"       ← in the VPC; reads only the app secret

                    Log retention, error alarm, monthly budget alarm

Browser (front end on localhost:4200) ──HTTPS──► HTTP API ──► api Lambda ──1433──► RDS
                                                       api Lambda ──443──► Secrets Manager endpoint
```

## Code changes (small, configuration-driven)

### 1. Connection string from Secrets Manager (API and migrator)

- **New configuration source** in `HomeLoan.Infrastructure`. When `Database:AppSecretArn` (and, for the migrator, `Database:AdminSecretArn`) is set, it reads the secret once at start-up using `AWSSDK.SecretsManager`. It then builds the connection string from the secret's username and password plus `Database:Host`, `Database:Port` and `Database:Name`.
- **When the setting is absent** (Docker, tests), nothing changes: `ConnectionStrings:HomeLoan` is used as today.
- **The password never enters an environment variable.** The function's environment holds only the secret ARN and the host.
- **Unit tests** use a fake secrets client: the connection string is built correctly, characters are escaped, and a missing field fails at start-up with a clear message.

### 2. Lambda entry point for the migrator

- `Program.cs` checks `AWS_LAMBDA_RUNTIME_API`. On Lambda it starts `LambdaBootstrap` with a handler that calls the existing `DatabaseMigrator.Migrate`. Otherwise it behaves as the console app it is today.
- It is idempotent, so it is safe to run on every deploy.
- **Packages:** `Amazon.Lambda.RuntimeSupport` and `Amazon.Lambda.Serialization.SystemTextJson`.

### 3. Dockerfile targets

- **`lambda` and `migrator-lambda`.** The build stage uses `FROM --platform=$BUILDPLATFORM` and `dotnet publish -r linux-arm64`, so arm64 images are built on GitHub's x64 runners **without emulation**. The API is compiled ahead of time (ReadyToRun) to cut cold-start time.
- **Final stage:** `public.ecr.aws/lambda/dotnet:8`, with `COPY` steps only. `CMD ["HomeLoan.Api"]` uses the executable-assembly handler, so `AddAWSLambdaHosting` takes over.
- **Time zones:** `/usr/share/zoneinfo` is copied from the build stage, so `Australia/Sydney` resolves. That avoids a `RUN dnf install` in the arm64 stage.
- **Checked locally before AWS:** the Lambda base image includes the Runtime Interface Emulator. A script runs the image and posts an API Gateway HTTP API event to it, proving start-up, ICU, tzdata and routing on this Mac.

### 4. Front end

- `config/aws/config.json`, with `apiBaseUrl` set to the deployed URL, and an `npm run start:aws` script.
- The pipeline writes that file from the stack output. `scripts/write-aws-config.sh` does the same locally using the `huskystudio` profile.
- **CORS:** handled by the app (`Cors__AllowedOrigins=http://localhost:4200`), exactly as locally. API Gateway's own CORS is left off, so the two can't conflict.

**Settings (with reasons):**

| Setting | Value | Why |
|---|---|---|
| VPC | 2 AZs, `PRIVATE_ISOLATED` subnets, 0 NAT | RDS needs two subnet AZs. No NAT saves about US$45/month; nothing needs the internet. |
| RDS | `sqlserver-ex` 16.00, `db.t3.micro`, gp3 20 GB, `storageEncrypted`, not publicly accessible, 1-day backups | Smallest and cheapest option, still encrypted and private. |
| RDS removal | `RemovalPolicy.DESTROY`, no deletion protection, no final snapshot | An exercise environment that must tear down cleanly. NOTES says production would use RETAIN, deletion protection, snapshots and Multi-AZ. |
| App secret | Generated, 32 characters, excluding `;'"=,{}` | Those characters would break a connection string or the SQL literal. |
| Lambda `api` | arm64, 1769 MB (was 1024; see cold starts below), 15 s timeout, reserved concurrency 10, `live` alias with 1 provisioned instance | More memory means more CPU and a faster cold start. The concurrency cap protects the database's connection limit and the bill. |
| Lambda `migrator` | arm64, 512 MB, 5 min timeout | DbUp plus `EnsureDatabase` on first run. |
| Migration trigger | `Triggers.Trigger`, runs after the database and secrets, re-runs when the image changes | Migrations are part of the deploy, not a separate step. |
| HTTP API | `$default` route to `api`; throttling 20 requests/s, burst 40; JSON access logs | There's no auth, so throttling limits abuse and cost. |
| Logs | 1-week retention for both functions and the access log | Logs don't accumulate cost. |
| Alarms | Lambda errors > 0 over 5 minutes; monthly budget alarm (see questions) | Visible failures and a cost guard. |

## Pipeline

**`ci.yml`** gains:
- an `infra` job: build, test and `cdk synth`, on every push and PR;
- a `deploy` job: `needs: [frontend, backend, infra, e2e, e2e-api]`, `if: github.ref == 'refs/heads/main' && github.event_name == 'push'`, with `concurrency: deploy-aws` (no cancel-in-progress) and `environment: aws`. The environment shows the URL in GitHub.

**Deploy job steps:**
1. `aws-actions/configure-aws-credentials` with `role-to-assume: ${{ vars.AWS_DEPLOY_ROLE_ARN }}` (a repo variable; an ARN isn't a secret). `permissions: id-token: write`.
2. `npx aws-cdk@<pinned> deploy --all --require-approval never --outputs-file cdk-outputs.json`. CDK builds and pushes the images and runs the migration trigger.
3. **Smoke test** (`scripts/smoke-test.sh <url>`):
   - `/health/ready`;
   - on application **900001**: PUT loan details (201), GET (200 plus ETag), PUT applicants, GET, PUT without `If-Match` (428), DELETE (204).
   - Using application 900001 means demo data in application 1 isn't touched.
4. **Playwright against the live API.** Write `config/aws/config.json`, then run `E2E_CONFIGURATION=aws npm run e2e`. The reset calls `DELETE` on the deployed API. ~~This deletes application 1, so the demo data is reset on each deploy.~~ Changed after it wiped a manual test (ai-log #16): the journeys now use their own application, `900100`, set through `config.json`.
5. A job summary with the API URL and the commands to run the front end against it.

**`destroy.yml`:** `workflow_dispatch`, requiring the input `destroy` typed in, then `cdk destroy --all --force` (the database included). The bootstrap and OIDC stacks are kept, so a later push can redeploy.

| Risk | Check |
|---|---|
| ICU and tzdata missing in the Lambda base image (SqlClient, `Australia/Sydney`) | The local Runtime Interface Emulator run before any deploy; `/health/ready` in the smoke test |

| Cold start (container plus VPC plus .NET) about 1–3 s | ReadyToRun; then measured and reduced (1769 MB, overlapped secret fetch, 1 provisioned instance). Numbers below and in NOTES. |
| Two pushes in a row | `concurrency: deploy-aws` queues the second |
| A failed migration | The Trigger fails, so CloudFormation rolls back the API stack and the previous version keeps serving |

- **Deviations from the plan:**
  - Memory went to 1769 MB.
  - API Gateway now calls a `live` alias, because provisioned concurrency needs a version or alias.
  - Provisioned concurrency is on, about US$15–20/month; turn it off with `apiProvisionedConcurrency: "0"`.
- **The measurement tooling needed two fixes** (ai-log #13): the start-up timings must be logged before `RunAsync`, because `ApplicationStarted` never fires under the Lambda adapter; and bursts of traffic can't force cold starts.
- **Remaining gap:** About you loads two resources in parallel, so one user can still meet one on-demand cold start. Two instances would close it.
