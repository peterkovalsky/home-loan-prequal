# AI log

These are real cases where AI output (Claude Code) was wrong, incomplete, or needed steering, and how each was caught. Entries are added as they happen. A summary goes into `NOTES.md`.

| # | Phase | What the AI proposed | What was wrong | How it was caught | Outcome |
|---|---|---|---|---|---|
| 1 | Planning | Treat "keep it simple" as a virtue: no MediatR, no generic repository, no metadata-driven forms, with little else in their place. | It undershot the brief ("structure it like real production code", "so it can grow"). The reasoning was "less is better", not a cost-benefit case for each pattern. | Reviewing the plan against the brief and the assessment criteria. | Plan revised to name the production patterns that are included (layering, handlers, FluentValidation, ProblemDetails, unit of work, ETags, TimeProvider, runtime config) and to give a specific reason for each one left out. |
| 2 | Phase 1 (About you specs) | A spec named "keeps an applicant hidden by a smaller count…" whose body set up spies and asserted nothing, plus a redundant first test calling `TestBed.resetTestingModule()` mid-test. | A test that can't fail looks like coverage but isn't. | Self-review, reading the spec back before running it. | Replaced with a real scenario: Couple, then Single, then Couple restores applicant 2. |
| 3 | Phase 1 (About you specs) | The rewritten hidden-applicant test passed, but would still have passed with the feature deleted (the draft was never rewritten during the single-applicant visit). | It checked the outcome without exercising the code path. | Self-review: asked whether the test would fail if the feature were removed, and traced that it would not. | Test now edits during the single-applicant visit. Mutation check run: with `...this.hiddenApplicants` removed the test fails; restored, it passes. |
| 4 | Phase 2 planning | The overview put a single `rowversion` on `Application` as the ETag for every sub-resource. | Saving Loan details would change the version the client holds for applicants. Back, then Continue, then saving About you would get a false `412`, because the store keeps applicants (and their ETag) cached. | Self-review while detailing the concurrency design: traced the Back/Continue journey against the ETag the client would send. | One `rowversion` per resource: `LoanDetails.RowVersion`, plus an `ApplicantSet` row that owns the applicants. Recorded in `02-backend.md` under "Changes from the overview". |
| 5 | Phase 2 (API) | Minimal API endpoints bound the JSON body with the framework defaults. | Malformed JSON returned **500**. In Development, minimal APIs throw `BadHttpRequestException`, which fell through to the generic error handler. In Production the same request would have returned an empty 400, so the behaviour differed by environment. | A manual curl smoke test (`-d '{"applicants":['`), before any integration test existed. | `ThrowOnBadRequest` forced on everywhere, plus a `BadRequestExceptionHandler` returning a 400 ProblemDetails without echoing parser internals. An integration test will cover it. |
| 6 | Phase 2 (API) | The fix for #5 handled `BadHttpRequestException` in an `IExceptionHandler`. | The status code was right, but in .NET 8 the exception handler middleware logs every exception at **Error** level with a stack trace before any handler runs. Every malformed client request would have created error-level noise (and alerts) in CloudWatch. | Reading the integration test output: the malformed-JSON tests passed, but printed error logs with stack traces. | Moved to a `BadRequestMiddleware` inside `UseExceptionHandler`, which logs at Information. Re-ran the tests: no error-level logs. |
| 7 | Phase 2 (unit of work) | `DbSession` left a failed save's transaction open until the request scope was disposed, and rolled it back unconditionally there. | On CI (not reproducible locally under emulation) a request's dispose threw "This SqlTransaction has completed", because SQL Server had already ended it. Leaving the transaction open until after the response also meant locks outlived the request from the client's point of view. Root cause not fully proven: no deadlock or error was logged. The leading theory is lock contention between a lingering transaction from the previous race round and the next one. | A CI failure in the race test's set-up request (`ConcurrencyTests.cs:21`), read from the Actions log. | Handlers now roll back as soon as a save fails. Dispose skips rollback for a transaction the server has already ended and logs a Warning, so a future occurrence is diagnosable. Race rounds raised from 5 to 20 in CI. |
| 8 | Phase 3 (Lambda image) | `DbSession` implemented only `IAsyncDisposable`, which is fine under Kestrel. | The AWS Lambda ASP.NET Core adapter disposes request scopes **synchronously**, so every database request on Lambda would have thrown "type only implements IAsyncDisposable". No test caught it: all tests and Docker Compose host the API on Kestrel. | The local Lambda Runtime Interface Emulator check (`backend/scripts/lambda-local-check.sh`), run before any AWS deploy. | `DbSession` also implements `IDisposable` (synchronous rollback and dispose). A unit test disposes it the way the adapter does. |
| 9 | Phase 3 (Lambda image) | The plan said the Lambda base image has no time-zone database, so the Dockerfile copied Debian's `/usr/share/zoneinfo` into it. | Wrong assumption: AL2023's image already has tzdata, and the copy collided (`posix/Africa` is a directory there, a symlink in Debian). | The image build failed. | Copy removed. The emulator check proves `Australia/Sydney` resolves, because the API refuses to start otherwise. |
| 10 | Phase 3 (CDK) | Ran `cdk synth` without `--profile huskystudio`, straight after promising every AWS command would be pinned to that profile. | CDK fell back to the **default profile (`aaron-dev`, a different account)** and tried to assume a lookup role in the target account. AWS denied it, so nothing was created or changed. But it was the wrong identity, and the synth also needed AWS access at all because CDK wanted to look up the region's availability zones. | The synth output showed `aaron-dev` and account 801347848037. | `infra/cdk.sh` sets `AWS_PROFILE=huskystudio` and refuses to run if the caller's account isn't the one in `cdk.json`. Availability zones are committed in `cdk.context.json`, so synth needs no credentials. Verified by running synth with all AWS config disabled. |
| 11 | Phase 3 (first deploy) | The OIDC trust condition used the classic GitHub subject, `repo:<owner>/<repo>:environment:aws`. | This repository uses GitHub's **immutable subject** format, `repo:<owner>@<owner id>/<repo>@<repo id>:...`, so AWS refused `AssumeRoleWithWebIdentity` and the first deploy failed at sign-in. The template test passed, because it asserted the same wrong string the code produced. | The first deploy run failed. Then `gh api .../actions/oidc/customization/sub` (read-only) showed the real prefix. | `githubSubjectPrefix` added to `cdk.json`, with the trust and the test updated, and the OIDC stack redeployed. The test is only as good as its expected value: the expected subject is now taken from GitHub's API, not from memory. |
| 12 | Phase 3 (first deploy) | CORS on the deployed API allowed only `http://localhost:4200`. | The Playwright suite serves the front end on port **4300**, so every save against the live API was blocked by CORS, and all journeys failed at "Continue". The Compose E2E job couldn't catch it, because there the dev server proxies `/api`, which is same-origin. | The deploy job's Playwright step, then a curl preflight with `Origin: http://localhost:4300` against the live API, which returned no `Access-Control-Allow-Origin`. | `allowedOrigins` now lists both local ports. The live E2E run is the only test that exercises cross-origin calls, which is why it exists. |
| 13 | Cold starts (measurement) | Logged the start-up phase timings from `ApplicationStarted`, verified by running the API locally on Kestrel. The measurement script then forced "cold starts" with 8 background curls. | Under the Lambda hosting adapter, starting the server runs the Lambda runtime loop and never returns, so `ApplicationStarted` never fires: no timings were logged on AWS. The 8 requests caused no cold starts at all, because a warm instance answers in milliseconds and three warm instances absorbed them. The script also counted every first-SQL line twice, because the JSON console logger repeats the message inside `State`. | The first measurement run reported 0 cold starts. Reading the raw log streams showed no timings line even for real cold starts. Reproduced under the Runtime Interface Emulator. | Timings are logged just before `RunAsync` (Lambda's INIT Duration minus that total is the host's own start). The script now summarises the real cold starts of the live version over a time window, with regexes anchored to the top-level message. Verified under the emulator before deploying. |
