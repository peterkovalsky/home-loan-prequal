# AI log

These are real cases where AI output (Claude Code) was wrong, incomplete, or needed steering, and how each was caught. Entries are added as they happen. A summary goes into `NOTES.md`.

| # | Phase | What the AI proposed | What was wrong | How it was caught | Outcome |
|---|---|---|---|---|---|
| 1 | Planning | Treat "keep it simple" as a virtue: no MediatR, no generic repository, no metadata-driven forms, with little else in their place. | It undershot the brief ("structure it like real production code", "so it can grow"). The reasoning was "less is better", not a cost-benefit case for each pattern. | Reviewing the plan against the brief and the assessment criteria. | Plan revised to name the production patterns that are included (layering, handlers, FluentValidation, ProblemDetails, unit of work, ETags, TimeProvider, runtime config) and to give a specific reason for each one left out. |
| 2 | Phase 1 (About you specs) | A spec named "keeps an applicant hidden by a smaller count…" whose body set up spies and asserted nothing, plus a redundant first test calling `TestBed.resetTestingModule()` mid-test. | A test that can't fail looks like coverage but isn't. | Self-review, reading the spec back before running it. | Replaced with a real scenario: Couple, then Single, then Couple restores applicant 2. |
| 3 | Phase 1 (About you specs) | The rewritten hidden-applicant test passed, but would still have passed with the feature deleted (the draft was never rewritten during the single-applicant visit). | It checked the outcome without exercising the code path. | Self-review: asked whether the test would fail if the feature were removed, and traced that it would not. | Test now edits during the single-applicant visit. Mutation check run: with `...this.hiddenApplicants` removed the test fails; restored, it passes. |
| 4 | Phase 2 planning | The overview put a single `rowversion` on `Application` as the ETag for every sub-resource. | Saving Loan details would change the version the client holds for applicants. Back, then Continue, then saving About you would get a false `412`, because the store keeps applicants (and their ETag) cached. | Self-review while detailing the concurrency design: traced the Back/Continue journey against the ETag the client would send. | One `rowversion` per resource: `LoanDetails.RowVersion`, plus an `ApplicantSet` row that owns the applicants. Recorded in `02-backend.md` under "Changes from the overview". |
